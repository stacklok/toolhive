Delegated Credential Access

Agents acting for a user need that user's stored provider connections (their GitHub or Slack tokens) at the gateway, without a browser session. Today only interactive sign-ins get them. This proposal adds two more ways in, through the same subject mapping, actor checks and credential store.

Three ways a token reaches a user's credentials

Interactive

user → gateway AS → vMCP

Works today. Unchanged.

Delegated

agent platform AS-1 → ID-JAG → gateway AS-2 → short token → vMCP

AS-2 redeems an identity assertion and issues a gateway token for the native user. Scheduled runs use this path too.

Direct

customer IdP (Okta) → token → vMCP

The agent presents its Okta token straight to the gateway. Nothing in ToolHive mints a token in between.

All three end the same way: the subject is the native user, the actor is checked, and the credential is read by (gateway, user, routed provider) with an owner check. None can reach credentials through another's path.

Three decisions

Subject

One subject resolver

(issuer, binding claim, value) → native user. Never creates a user, fails closed. Binding claim per issuer: Okta uid, Entra oid, AS-1 upstream_subject. Never the email. A directory lookup is one implementation.

Actor

Three separate checks

Proof at ID-JAG issuance (the existing validator hook). Client checks: client_id binding at redemption; a required client allowlist (Okta cid) on the direct path, reusing token exchange's existing one. Policy on the outermost act, one interface for redemption, exchange and direct. act.iss must match the assertion's issuer.

Storage

One user-keyed store

Rows keyed by (gateway, user, provider), as a storage decorator behind a setting. No new storage methods, so existing decorators keep working. An injected reader fetches only the routed provider and answers "needs authorization" when it is missing.

Who may read a user's credentials

Each route needs positive proof. A token is never admitted because a claim is missing.

RouteAdmitted whenUserRead
interactiveissued by the gateway's AS and carries tsidsuball providers, as today

directconfigured issuer, same IdP tenant as sign-in; exact aud; client allowlist; actor required; scopes; lifetime cap; DPoP when bound; no tsid or markerresolved per requestrouted provider only

The marker is issued only by the gateway's own AS after resolution, client and actor checks pass, and in external mode only with the user's approval. Never at login, and never because may_act or a wildcard matched. A marked token cannot be exchanged again and gets no refresh token.

What changes where

ToolHive

  • New pkg/auth/subject and pkg/auth/actor interfaces
  • Redemption and exchange: per-issuer subject mode and binding claim, marker
  • Read service GetValidTokensForUser, admission route on the identity
  • Direct-issuer route at the vMCP (or an in-process exchange, see D5)
  • Optional user-keying decorator for standalone installs

Embedders

  • Gateway with a directory: nothing required to keep working; implements the resolver and actor policy against its directory to adopt the new routes
  • Agent platform (AS-1): wires its actor validator, one actor ID per agent, agrees the binding-claim name with the gateway

Compatibility

  • Embedders that already key rows by user: no change on upgrade. No storage interface changes, the interactive validator path and its bulk load stay, tsid stays in tokens, and every new behaviour is off until configured per issuer.
  • Standalone ToolHive: user keying behind a setting, default unchanged. On switching, every replica upgrades first, then each user signs in once. One-way.
  • Everyone: one behaviour change, the refresher deletes a row after a failed refresh-token rotation only if the row still holds the token it redeemed.
